## 一、项目概述

### 1.1 选题背景

dizzylab.net 是国内知名的独立音乐数字发行平台，汇集了大量同人音乐社团（Circle）及其发行的专辑作品。平台数据涵盖专辑信息、曲目试听、社团资料、用户互动等多个维度，数据结构丰富且具有典型性，适合作为爬虫课程设计的目标站点。

本项目旨在设计并实现一套完整的定向网络爬虫系统，系统性地采集 dizzylab 平台的公开数据，为后续的音乐推荐、数据分析等应用提供数据基础。

### 1.2 项目功能

本系统实现以下核心功能：

1. **专辑数据批量采集**：从平台 API 获取专辑列表，逐张爬取专辑详情页，提取标题、价格、发布日期、封面等结构化字段
2. **音频试听文件下载**：下载每张专辑的试听 MP3 音频，上传至 MinIO 对象存储，记录文件路径和大小
3. **社团信息采集**：爬取社团详情页，提取社团描述、Logo、成员列表
4. **用户角色识别**：从 Setup 页解析 STAFF/PRO 用户角色标记
5. **用户行为数据采集**：爬取用户的已购专辑、收藏列表、关注社团三个维度的数据
6. **增量更新机制**：支持全量爬取和增量爬取两种模式，智能跳过已有数据

### 1.3 爬取网站介绍

dizzylab.net 是一个独立音乐数字发行平台，主要特点：
- **公开访问**：所有专辑详情页、社团页面、用户公开页面均无需登录即可访问
- **API + HTML 混合**：专辑列表通过 JSON API 提供，详情页为服务端渲染 HTML
- **音频试听**：每张专辑提供低码率 MP3 试听，通过 CDN 分发
- **数据关联丰富**：专辑 ↔ 社团 ↔ 用户 ↔ 标签之间存在多对多关系

## 三、项目总体设计

### 3.1 系统架构

```
┌─────────────────────────────────────────────────────┐
│                    爬虫调度层                         │
│  album_bulk / album_incremental / circle /           │
│  user_roles / user_pages                             │
├─────────────────────────────────────────────────────┤
│                    基础设施层                         │
│  DbSpiderMixin    StorageBackend    ItemRegistry     │
├─────────────────────────────────────────────────────┤
│                    持久化层                           │
│  Repository（统一 DB 读写 + FK 缓存）                 │
│  PostgresPipeline（Item 注册表调度）                   │
├──────────────┬──────────────────┬───────────────────┤
│  PostgreSQL  │     MinIO        │    Scrapy 引擎     │
└──────────────┴──────────────────┴───────────────────┘
```

### 3.2 爬取思路

系统采用 **分层爬取** 策略，按数据依赖关系分阶段执行：

```
第一阶段：专辑数据铺底
  API 专辑列表 → 专辑详情页 → 曲目/标签/社团/评论/已购用户

第二阶段：社团信息补充
  读取 circles 表 → 社团详情页 → 描述/Logo/成员

第三阶段：用户角色标记
  Setup 页 → STAFF/PRO 角色

第四阶段：用户行为数据
  用户已购/收藏/关注 → 三个维度页面爬取
```

| 注册表 | `item_registry.py` | Item 类型 → (解析, 写入) 函数注册 |
| Pipeline | `pipelines.py` | 注册表调度 + 写入计数汇总 |
| 存储抽象 | `storage.py` | MinIO 生产后端 + 测试用内存后端 |

## 四、核心功能实现详解

### 4.1 爬虫框架搭建与配置（对应考核模块 1）

#### 4.1.1 项目结构

采用 Scrapy 标准项目结构，扩展了 `repository.py`、`item_registry.py`、`storage.py` 等自定义模块，实现关注点分离。

#### 4.1.2 基础配置

**settings.py** 延迟加载配置，避免 import 时读文件：

```python
DOWNLOAD_DELAY = 3          # 同域名请求间隔 3 秒
CONCURRENT_REQUESTS_PER_DOMAIN = 1  # 单域名串行
ROBOTSTXT_OBEY = False      # dizzylab robots.txt 禁用 /*?*
COOKIES_ENABLED = False     # 不需要 Cookie
RETRY_TIMES = 3             # 失败重试 3 次
RETRY_HTTP_CODES = [500, 502, 503, 504, 522, 524, 408, 429]
```

**反爬策略**：
- User-Agent 伪装为 Chrome 浏览器
- 请求间隔 ≥ 3 秒（可通过 `delay.json` 切换策略：default/gentle/test）
- 专辑间延迟 60~120 秒，曲目间延迟 2~7 秒
- 单域名并发 = 1，完全串行访问

#### 4.1.3 延迟策略配置

通过 `config/delay.json` 实现多策略切换：

```json
{
  "active": "default",
  "strategies": {
    "default": { "download_delay": 3, "between_albums_min": 60, ... },
    "gentle":  { "download_delay": 5, "between_albums_min": 120, ... },
    "test":    { "download_delay": 1, "between_albums_min": 10, ... }
  }
}
```

### 4.2 网页基础数据爬取（对应考核模块 2）

#### 4.2.1 专辑列表 API

```
GET https://www.dizzylab.net/apis/getdiscs/?l={start}&r={end}&sort=ad&type=album
```

返回 JSON，每条记录包含 `id`（slug）、`title`、`price`、`cover`、`label`（社团名）、`labelid` 等字段。翻页通过 `l`（起始位置）和 `r`（结束位置）参数控制，每页 24 条。

#### 4.2.2 专辑详情页解析

使用 XPath 从 HTML 中提取结构化数据：

```python
# 专辑描述段落
info_p = response.xpath("//p[@class='text-left' and contains(@style,'margin-top:32px')]")
# 发布日期
pub_text = response.xpath("//text()[contains(., '发布于')]").get()
# 封面图（懒加载属性）
cover = response.xpath("//img[@id='imgsrc0']/@data-src").get()
```

**提取字段**（超过 5 项，满足考核要求）：

| 字段 | 来源 | 解析方式 |
|:---|:---|:---|
| 标题 | API `title` | 直接取值 |
| 价格 | API `price` | `float()` 转换（异常回退 0.0） |
| 描述 | 详情页 `<p>` | XPath + HTML 清洗 |
| 发布日期 | 详情页文本 | 正则 `(\d{4})年(\d{1,2})月(\d{1,2})日` |
| 封面 URL | 详情页 `<img>` | XPath 取 `data-src` 属性 |
| 社团名 | API `label` | 直接取值 |
| 标签 | 详情页 `<h4><a>` | XPath + `strip("#")` |

#### 4.2.3 错误处理

统一使用两个保护函数：

```python
def check_response_ok(response) -> bool:
    """HTTP 400+ 返回 False，3xx 不阻断"""
    if response.status >= 400:
        logger.warning("HTTP %d: %s", response.status, response.url)
        return False
    return True

def safe_json_load(response) -> dict | None:
    """JSON 解析失败返回 None"""
    try:
        return json.loads(response.text)
    except (json.JSONDecodeError, ValueError):
        return None
```

### 4.3 JavaScript 动态渲染数据获取（对应考核模块 3）

dizzylab 平台的**专辑列表数据通过 Ajax API 异步加载**，前端通过 JavaScript 发起 `/apis/getdiscs/` 请求获取 JSON 数据后动态渲染页面。

本项目通过**接口逆向解析**方式获取动态数据：

1. 使用浏览器开发者工具（F12 → Network）分析页面加载流程
2. 发现专辑列表数据来源于 `/apis/getdiscs/` JSON API
3. 直接请求该 API 接口，获取结构化 JSON 数据
4. 绕过前端 JavaScript 渲染，直接解析 API 响应

同样，已购用户（`/albums/getbuyers/`）和评论（`/albums/getdisccomment/`）也通过 Ajax API 异步加载，均采用接口逆向方式获取。

### 4.4 多页数据批量爬取（对应考核模块 4）

#### 4.4.1 翻页机制

专辑列表 API 使用位置参数翻页：

```
第 1 页：l=0&r=24
第 2 页：l=24&r=48
第 3 页：l=48&r=72
...
```

每页 24 条（`PAGE_SIZE = 24`），自动递增直到 API 返回空数据。

#### 4.4.2 队列驱动调度

`album_bulk` 爬虫采用队列驱动 + `reactor.callLater` 的非阻塞调度模式：

```python
def _process_next_disc(self):
    """从队列取出下一张专辑并注入引擎"""
    if self._pending_discs:
        disc = self._pending_discs.pop(0)
        self.crawler.engine.crawl(scrapy.Request(...))
```

`_spider_idle` 信号处理器在引擎空闲时自动触发下一张专辑的调度，专辑间延迟通过 `reactor.callLater` 实现，不阻塞 Twisted reactor。

#### 4.4.3 增量爬取

`album_incremental` 爬虫从最新页开始，遇到数据库中已存在的专辑立即停止：

```python
if self._album_is_complete(slug):
    raise CloseSpider(f"已追平最新数据（{slug} 已完整爬取）")
```

用户页面爬虫通过 `userpage_crawled_at` 字段实现 30 天增量跳过。

### 4.5 数据解析与精准提取（对应考核模块 5）

#### 4.5.1 解析技术

| 技术 | 应用场景 |
|:---|:---|
| **XPath** | 专辑详情页、社团详情页、用户页面的 HTML 解析 |
| **正则表达式** | 曲目标题解析、发布日期提取、用户 ID 提取、URL 匹配 |
| **JSON 解析** | API 响应数据解析 |

#### 4.5.2 曲目标题解析

```python
TRACK_RE = re.compile(r"^\d+\.\s*(.+?)\s*\((\d{1,2}:\d{2})\)$")

# "1. 冬临之时 - Static World (02:48)"
# → file_name = "冬临之时 - Static World", track_length = "02:48"
```

#### 4.5.3 数据清洗

- HTML 标签去除：`re.sub(r'<[^>]+>', '', text)`
- `<br>` 转换：`re.sub(r'<br\s*/?>', '\n', text)`
- 标签去前导 `#`：`raw.lstrip("#").strip()`
- 头像 URL 去外层引号：`avatar.strip('"')`
- 社团名 URL 解码：`unquote(name)`

#### 4.5.4 提取字段统计

| 数据实体 | 提取字段数 | 字段列表 |
|:---|:---|:---|
| Album | 7 | dizzylab_id, title, info_title, info_content, price, cover_url, publish_date |
| WorkFile | 6 | file_name, object_key, file_type, track_length, file_size, sort_order |
| Circle | 4 | dizzylab_labelid, name, description, logo_url |
| User | 4 | dizzylab_user_id, username, avatar_url, user_role |
| Tag | 1 | name |
| Comment | 3 | user_id, album_id, content |

### 4.6 数据库持久化存储（对应考核模块 6）

#### 4.6.1 数据库设计

共 12 张表，采用 SERIAL 主键 + dizzylab 业务键 UNIQUE 约束：

```sql
CREATE TABLE albums (
    album_id      SERIAL PRIMARY KEY,
    dizzylab_id   VARCHAR(50) UNIQUE NOT NULL,
    title         VARCHAR(200) NOT NULL,
    info_title    TEXT,
    info_content  TEXT,
    price         DECIMAL(10,2),
    cover_url     VARCHAR(500),
    publish_date  TIMESTAMP
);
```

#### 4.6.2 去重策略

| 表 | 去重方式 |
|:---|:---|
| albums / circles / users / tags | `ON CONFLICT ... DO UPDATE`（Upsert） |
| work_files | `DELETE + INSERT`（按 album_id 刷新） |
| 关联表 | `ON CONFLICT DO NOTHING` |

#### 4.6.3 FK 缓存机制

Pipeline 维护 4 个内存缓存字典，避免对同一 dizzylab_id 反复查询：

```python
self._album_id_cache: dict[str, int] = {}    # dizzylab_id → album_id
self._circle_id_cache: dict[int, int] = {}   # dizzylab_labelid → circle_id
self._user_id_cache: dict[int, int] = {}     # dizzylab_user_id → user_id
self._tag_id_cache: dict[str, int] = {}      # tag_name → tag_id
```

缓存未命中时从 DB 回退查询并回填，解决爬虫重启后缓存为空的问题。

#### 4.6.4 批量写入

每张专辑的数据（专辑本体 + 曲目 + 标签 + 社团 + 评论 + 已购用户）在同一个 Pipeline 事务中写入，确保数据一致性。Pipeline 关闭时打印写入汇总：

```
Pipeline 写入汇总: AlbumItem=50 | WorkFileItem=320 | TagItem=150 | CircleItem=30 | ...
```

## 六、问题与解决方案

### 6.1 反爬策略应对

**问题**：dizzylab 对高频请求有访问限制。

**解决方案**：
- 配置三级延迟策略（default/gentle/test），最小请求间隔 3 秒
- 专辑间延迟 60~120 秒，完全串行访问
- User-Agent 伪装为 Chrome 浏览器
- 失败自动重试 3 次

### 6.2 动态数据获取

**问题**：专辑列表、已购用户、评论数据均为 Ajax 异步加载，静态请求无法获取。

**解决方案**：通过浏览器 Network 面板分析 API 接口，直接请求 JSON API 端点，绕过前端 JavaScript 渲染。

### 6.3 大规模数据调度

**问题**：数百张专辑逐张爬取，需要非阻塞调度。

**解决方案**：采用队列驱动 + `reactor.callLater` 模式。引擎空闲时从队列取出下一张专辑注入，延迟通过 Twisted 定时器实现，不阻塞 reactor 线程。

### 6.4 外键关联解析

**问题**：12 种 Item 之间存在外键关联（如 WorkFile → Album），Spider yield 时 DB 主键未知。

**解决方案**：使用 `_dizzylab_*` 临时字段暂存业务键，Pipeline 通过内存缓存映射为 DB 主键。缓存未命中时自动回退查询 DB。

### 6.5 音频文件存储

**问题**：试听音频需要从 CDN 下载后持久化存储。

**解决方案**：设计 `StorageBackend` 抽象接口，生产环境用 MinIO 后端，测试环境用内存后端。音频文件按 `audio/preview/{album_slug}/{sort_order:03d}.mp3` 命名。

### 6.6 增量更新

**问题**：全量重爬耗时过长，需要增量更新机制。

**解决方案**：
- 专辑爬虫：检查 `info_title IS NOT NULL` 判断完整性
- 增量爬虫：从最新页开始，遇到已存在专辑即停止
- 用户页面：`userpage_crawled_at` 字段标记爬取时间，30 天内跳过

## 七、课程学习总结与心得体会

### 7.1 技术收获

1. **Scrapy 框架深入理解**：掌握了 Spider、Pipeline、Middleware、信号机制等核心概念，理解了 Twisted 异步编程模型
2. **接口逆向分析**：学会了使用浏览器开发者工具分析 Ajax API，直接请求 JSON 数据
3. **数据库设计实践**：设计了 12 张关联表，使用 Upsert 实现幂等写入，内存缓存优化查询性能
4. **工程化思维**：通过模块化设计（Repository、ItemRegistry、StorageBackend）实现了关注点分离，提高了代码可测试性

### 7.2 工程实践感悟

1. **合规性优先**：合理设置请求间隔，仅采集公开数据，不给目标服务器造成压力
2. **错误处理的重要性**：网络请求、数据解析、数据库写入等环节都可能出现异常，完善的错误处理是系统稳定运行的保障
3. **增量设计的价值**：全量重爬代价高昂，增量更新机制大幅提升了日常数据同步效率
4. **测试驱动质量**：编写了 195 个单元测试，覆盖所有核心模块，在重构时提供了信心保障

### 7.3 不足与改进方向

1. **异步优化**：当前音频下载使用同步 `requests.get()`，未来可改为 Twisted 异步下载
2. **分布式扩展**：当前为单机运行，未来可考虑 Scrapy-Redis 实现分布式爬取
3. **数据质量监控**：可增加数据完整性校验和爬取成功率统计
